# PMBA repo — workflow

This repo (github.com/xlantz/pmba) is the source of truth for the PMBA Field Guide.
The claude.ai Project pulls from it via the GitHub integration; edits are NOT made in the Project.

Site lives in `pmba-field-guide/` (static HTML; shared JS data in `pmba-field-guide/assets/`).

When making changes:
1. `git pull --ff-only` first — other sessions (e.g. cloud Claude branches) may have pushed.
2. Edit files, then commit to `main` with the message style `update MM.DD.YY` (or a short descriptive message for larger additions).
3. `git push origin main`, then remind the user to click **Sync** in the claude.ai Project.

## Zip drops from claude.ai
The user often builds pages in claude.ai chat and attaches the downloaded zip (e.g. `pmba-field-guide (12).zip`)
here. Its root matches `pmba-field-guide/` (HTML files at top level, plus `assets/`). To apply one:
1. `git pull --ff-only`, then extract the zip to a temp folder (not into the repo).
2. Compare against `pmba-field-guide/` with `git diff --no-index --stat --ignore-cr-at-eol`. Most files differ only
   in line endings (zip is LF, repo is CRLF); ignore those.
3. Look at the real diffs. If the zip *removes* content that's on GitHub (e.g. work pushed from another session),
   stop and ask before overwriting. Otherwise copy only the genuinely changed/new files.
4. If the zip is missing files that exist in the repo, do NOT delete them unless the user says so.
5. Commit (`update MM.DD.YY` + a one-line summary of what changed), push, summarize the changes for the user, and
   remind them to Sync the Project.

Zips built in claude.ai are usually based on the *previous zip*, not the synced repo, so they lack work pushed from
Claude Code. Find the base (compare a few shared files with the last zip and recent commits) and three-way merge each
changed file (`git merge-file`, ours = repo, base = that version, theirs = zip) instead of copying.

## Site menu: Semester 1 / Semester 2
Every page's top nav is Home | Semester 1 (collapsible course groups: MGT 6050, MGT 6051, ACCTG 6000, MKTG 6090,
Mock Tests) | Semester 2 | page-local links. It is maintained by `tools/semester-nav/apply_semester_nav.py`
(run as `python tools/semester-nav/apply_semester_nav.py pmba-field-guide`; it also writes `semester1.html` /
`semester2.html`). It lifts course links from each page's existing nav, so a NEW page must get a current nav first
(copy one from an existing page) or it will carry a stale menu. Add Semester 2 courses by editing `SEM2` in that script.
MGT 6051 Part 1 pages are `mgt6051-start.html`, `mgt6051-wk1..5.html`; `tools/semester-nav/build_mgt6051_mock.py
pmba-field-guide` regenerates its mock test after quiz edits. `wire.py` understands the semester layout (it rewrites
the MKTG 6090 group and the open/active state) and produces exactly what the semester script does, so running either
afterwards changes nothing. MGT 6051 AI policy (Canvas): study aids only; never draft reflections, papers or scripts.

## MKTG 6090 unit pages (generated)
`mktg-unit1.html` ... `mktg-unit10.html` and their `assets/mktg-unitN-*.js` files are GENERATED by `tools/mktg-units/`
(see its README). Never hand-edit them: edit `tools/mktg-units/units/uN/`, then run
`python tools/mktg-units/build.py N`, `python tools/mktg-units/wire.py`, `python tools/mktg-units/check.py`.
- `wire.py` also owns the MKTG menu on every page, the MKTG home-page cards (between `MKTG-UNITS` markers in
  `index.html`), the unit block at the end of `assets/mktg-mock-test-data.js`, and the mock-test page wording.
  If a zip or drop-in changes those areas, re-run `wire.py` afterwards rather than merging them by hand.
- The chapter pages (`mktgN.html`) remain as reference pages and are the source the unit pages copy from; after
  changing a chapter page, rebuild the units that include it.
- Case briefs (`case-emotiv`, `case-loreal`, `case-virgin-mobile`, `case-bbva`, `case-atlantic`) and the
  `mktg-math-note` reading are hand-built drop-in pages (not generated); `wire.py`'s EXTRAS list keeps them in the MKTG
  menu, and each unit's `uN_case` section links to its brief with the professor's prep questions. Course AI policy:
  no AI for quizzes, case analyses or MARKSTRAT, so case pages stay briefs only (facts, checked exhibits, frameworks,
  where to look) with no recommendations or final calculations. The Adobe case (Unit 5) and DDOM instructions were
  not provided.
- When new professor slides arrive (Units 7-10), add `uN_*` slide sections per the README; verify every number in
  Python and flag unreadable OCR rather than guessing; never invent case facts (case texts are not available).
